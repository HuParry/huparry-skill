# 通信题

## 先确定通信模型

不要把通信题一律改成交互命令。先保持原题定义：

- Run-Twice：A 完成后，将受限整数/串/染色等交给 B；同一程序运行两次，通过 first/second 或题目明确方式区分。
- 双向实时通信：需要双方多轮发送，精确定义轮次、发送者选择、预算与终止；不要用未计入预算的指令、消息长度或终止信号偷传信息。
- 多角色/多轮模式：按题面确定进程数及每人的私有输入，不机械固定为两人。

## Hydro manager 接口

`num_processes: k`。当前 Hydro 传入每个进程的两个参数，按角色顺序排列：

```text
manager fromA toA fromB toB ...
```

manager stdin 是裁判私有测试数据；fromX 是选手 stdout 的读端，toX 是选手 stdin 的写端。Hydro 的参数形如 `/proc/self/fd/3` 等；用 fdopen 接管继承描述符，确保 fclose 真正关闭该写端。不要对这类参数重新 fopen 导致原描述符仍开启、选手等不到 EOF。

manager stdout 输出 [0,1] 的得分比例（普通全点判定用 0/1），stderr 输出诊断。它不是 testlib interactor 的 quitf 协议。

## 公平性和隔离

- 仅传递题目允许的信息。整数应解析、检查范围后以规范数值转发；不转发其前导零、符号、空白等表面表示。
- 串、颜色、位置、次数、长度均按协议检查；不把原始私有输入或正确答案额外发送给 B。
- 若 B 的输入依赖 A 的输出（例如邻居颜色），仅依协议生成；预先固定的询问不能根据选手策略擅自改变。
- 裁判应按原始问题语义检验结果，而不是只接受标程消息、固定染色或单一构造。
- 进程隔离由目标 OJ 提供；不能仅因本地程序声称不共享文件就宣称安全隔离已经验证。

## 管道与终止

- 批量输入可能超过管道缓冲区；若选手也批量输出，先写完全部再读可能相互阻塞。按具体接口决定阶段化、并发写入/读取或其他可靠方式。
- 向某进程写完所有输入后关闭对应写端，使使用 EOF 读取的解法能正常结束；读取所有合法输出后检查尾随内容。
- 并发写线程存在时，判错退出须避免常规 exit 的全局 FILE 刷新等待被写线程占用的阻塞管道。可在已刷新得分/诊断后使用 `_Exit`，或采用经测试的取消和关闭方案。
- 本地测试器应让转发线程独占其管道，不同时调用 communicate 抢读 stdout 或提前关闭 stdin。裁判判错后及时结束剩余选手；超时需回收进程，不能留下挂起任务。

## 验证

用真实 manager 与全部隔离选手进程跑满数据。额外验证合法但不同的消息/染色策略，预算的恰好边界和超界、非法字符、额外信息、提前退出和大批量双向 I/O。仅普通进程分别跑 first 与 second，不足以发现 EOF 与缓冲区死锁。

输出依赖选手通信策略时可以使用占位 `.out`，但必须在资料中注明其作用；只要 manager 实际依赖答案文件，就不能使用无意义占位。
